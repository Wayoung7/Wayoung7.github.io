## 过程（Procedures）

当程序进入一个新函数时，程序运行会跳转到新的代码块位置，相关数据被传入作用域，局部变量在栈上分配内存；当函数返回时，数据被返回，栈上的局部变量被清除，程序运行返回到函数被调用的位置。这就是所谓的**过程**。

### 栈

下一章会具体展开关于计算机内存的所有细节，在本章，我们可以简单的认为“**栈**”就是是计算机内存中的一块区域，我们都知道，栈是用来存储局部变量的地方。<u>**栈从上向下生长**</u>，所以**栈底**的地址*最大*，**栈顶**的地址*最小*。`%rsp`就是那个*特殊的*寄存器，用于存放栈顶的地址。

![栈](/img/cmu213/asm_stack.png)

### 控制转移（Control Transfer）

`%rip`寄存器用于存放当前执行的指令的地址（Program Counter）（*简称为PC*），调用函数时只需将`%rip`设为函数开始的位置，同时，我们还需要记录调用的位置，以便函数返回后能跳转到原来的指令，这个返回的地址也被存储在栈上。

汇编中，使用`call`指令调用函数，然后在函数中调用`ret`指令返回。下面是一个`call`和`ret`的例子，当执行`call`时，返回的地址被**压入栈**（PC减小，然后写入内存），函数返回时，所有的局部变量被清空，返回的地址被**弹出栈**，增大PC，然后跳转回函数调用的位置。

![call](/img/cmu213/asm_call.png)

### 数据转移

有些函数有**传参**和**返回值**，数据在函数调用之间是如何转移的呢？大部分情况下，只需要寄存器就够了。

- 第一到六个参数存放在寄存器`%rdi` `%rsi` `%rdx` `%rcx` `%r8` `%r9`中（整数和指针），如果超过六个，会在栈上开辟空间，通过栈来传参。
- 返回值存放在`%rax`中，如果一个寄存器存不下（例如返回一个包含两个`int`的`struct`），则存放在`%rax`和`%rdx`中，如果返回值大于`16`字节，函数调用者会开辟一块新的内存，然后把这块内存的地址**隐式地**通过第一个参数寄存器`%rdi`传给函数。

### 管理局部数据

在所有之前的例子中，局部变量都能存在**寄存器**中，并直接在寄存器中完成运算。*但有些时候我们必须使用栈来存储局部变量*。比如：

- 没有足够的寄存器来存储/将寄存器中的临时变量保存到内存中以便这个函数调用的函数使用寄存器
- 有些运算包含取地址`&`，必须得出变量实际存在内存中的地址
- array或struct

对于每个函数，在栈中必须有一个地方存放有关这个函数运行的所有信息，比如大于六个的参数、局部变量和返回的地址。因此每个函数在创建时都会在栈上开辟一块空间，称为**栈帧**（Frame），用于保存一个函数的状态.函数的调用就如同*叠盘子*，调用函数时创建栈帧盘子，叠到最上面，函数返回时从最上面拿走盘子。**调用**函数的帧称为$Caller Frame$，**被调用**的函数的帧称为$Callee Frame$。

下面是一个简单的例子，假设我们有C程序（重点关注Caller）：

```c
// Callee
// 交换xp和yp，并返回两者的和
long swap_add(long *xp, long *yp) {
    long x = *xp;
    long y = *yp;
    *xp = y;
    *yp = x;
    return x + y;
}

// Caller
long caller() {
    long arg1 = 534;
    long arg2 = 1057;
    long sum = swap_add(&arg1, &arg2);
    long diff = arg1 - arg2;
    return sum * diff;
}
```

下面是Caller的汇编：

```asm
caller:
    subq $16, %rsp       # rsp -= 16，在栈上开辟空间
    movq $534, (%rsp)    # *rsp = 534，将534存到rsp所指的位置
    movq $1057, 8(%rsp)  # *(rsp + 8) = 1057，将1057存到rsp+8所指的位置
    leaq 8(%rsp), %rsi   # rsi = &1057，传参2
    movq %rsp, %rdi      # rdi = &534，传参1
    call swap_add        # 调用swap_add，此时返回值已被存到rax，534和1057已交换
    movq (%rsp), %rdx    # rdx = *rsp = 1057
    subq 8(%rsp), %rdx   # rdx = rdx - *(rsp + 8) = rdx - 534
    imulq %rdx, %rax     # rax *= rdx
    addq $16, %rsp       # rsp += 16，释放内存
    ret
```

在Procedure中其实很大一部分的指令都是用于**准备**函数调用和函数调用结束后**获取**结果的。函数逐步的调用过程已经很清晰了：

![Swap Add](/img/cmu213/asm_swap_add.png)

书中对于**栈帧**一般结构的定义是这样的，已经不用再解释了：

![Stack Frame](/img/cmu213/asm_stack_frame.png)

### 寄存器存储约定

> 还有最后一个问题，Callee如何知道哪些寄存器是可用的（哪些寄存器被Caller占用了，所以Callee不能改变其中的值）？答案是Callee没法知道。因此我们需要制定一些约定，以防寄存器滥用。

使用寄存器有两种约定：
- **Caller Saved**：在Caller调用Callee之前，Caller要保存临时变量
- **Callee Saved**：Callee在运行过程中若要使用寄存器，则需保存寄存器中的初始值，在使用完成后将寄存器还原

x86-64 Linux 中的寄存器有这样的约定：
- `%rax` Caller Saved
- `%rdi` - `%r9` (参数) Caller Saved
- `%r10` `%r11` 临时变量 Caller Saved
- `%rbx` `%r12` `%r13` `%r14` 临时变量 **Callee** Saved
- `%rbp` （可能会用作）帧指针 **Callee** Saved

## 数组（Array）

### 数组的访问

C中有许多不同的数据类型，但在内存层面，这些类型并没有区别，类型只是对一块数据不同的解析方式。不同的数据类型有不同的长度，比如`int`为4字节、`long`为8字节……我们所说的一个变量的地址，其实是这个变量所占内存空间的**第一个字节的地址**。

C中的数组由`Type name[length];`创建，开辟了一块**连续**的**栈内存**空间，长度为`length * sizeof(Type)`。只要知道*数据类型*和*第一个元素的地址(即数组的地址)*，计算机就能通过简单的**地址计算**获得每一个元素的地址：`(%array, %index, 4)` $array+index\times sizeof(Type)$

在C中，对于一个指向数组的**指针的加减**会相应的自动*乘上元素的长度*，编译器则需要将其展开，具体到每一个字节的地址计算。

### 二维数组

`T A[R][C]`表示：

```
A[0][0]   ...   A[0][C-1]
   .                .
   .                .
   .                .
A[R-1][C] ...  A[R-1][C-1]
```

实际在内存中的存储方式是以每**一行**来存的：

![Array](/img/cmu213/asm_array.png)

访问一个元素同样是通过**地址计算**，只不过要计算*两次*。
`Arr[Row][Col];`
$$Mem[Arr+Row\times OuterSize + Col\times InnerSize]$$

另一个例子：

```c
Type cmu[5] = {...};
Type mit[5] = {...};
Type ucb[5] = {...};
// univ为一个指针的数组，每个指针都指向一个Type的数组
Type *univ[3] = {cmu, mit, ucb};
```

访问`Type`数据的方式为：
`univ[Row][Col];`
$$Mem[Mem[univ + Row \times 8] + Col * Sizeof(Type)]$$

*虽然C语言的语法是相同的，但计算机在背后干了不同的事。*

## 结构体（Structure）

```c
struct rec {
    int a[4];
    size_t i;
    struct rec *next;
};
```

在内存中：

```
 r
 |
 V
+---------------+-------+-------+
| a             | i     | next  |
+---------------+-------+-------+
 0               16      24      32
```

创建结构体时，在栈内存中开辟了一块连续的，能够包含所有fields的空间。fields在内存中的顺序即是struct声明的顺序。每个field的offset（地址）在编译阶段被编译器决定。

### 数据对齐

一般来说编译器都会将struct中的fields在内存中**对齐**。这是一个*非常重要*的过程。

#### 如何对齐

- struct中每个field的offset必须是其基本类型的长度的整数倍。
- 整个struct的长度必须是其中*最长的对齐长度*的整数倍。

下面是一个课件中的例子：

![Struct Align](/img/cmu213/asm_struct_align.png)

在对齐之后，field之间插入了一些间隔。比如，对于`i`来说，其基本类型是`int`长度为4，因此`i`的offset必须为4的倍数，又因为`c`占一个字节，因此`i`的offset只要调到4就行，所以在`c`后插入长度为3的间隔；`v`的类型是`double`长度为8，因此offset调到16。

![Struct Align Overall](/img/cmu213/asm_align_overall.png)

假设换一下field的顺序，虽然此时所有field都能连续存储了，但长度依然为24，因为需要满足第二个总体长度的条件，24是8的倍数。

#### 为什么要对齐

- 在对齐之后，大部分的变量都以4字节或8字节为一个单位读取（硬件层面、cpu指令层面更高效）
- 现代cpu的缓存一行一般为64字节，cpu通过缓存一行一行地访问内存数据，如果数据没有对齐，访问一个变量可能需要访问两个缓存行，非常低效
- 如果不对齐，数据可能跨虚拟内存分页

#### 通过对齐节省空间

显然，不同的field排列方式可能会使struct有不同的长度，如何节省空间，**只需要记住一条规律：field的顺序为从长度最长到最短**。

## 内存泄漏

### 缓冲区越界

*虽然现代编程语言（即便是C）都已经能阻止我们写出内存不安全的代码，但我觉得依然有必要理解一些程序时如何造成内存不安全的。*

假设我们有一个包含两个`int`和一个`double`的struct：

```c
typedef struct {
    int a[2];
    double d;
} struct_t;

double fun(int i) {
    volatile struct_t s;  // volatile让编译器不要优化s
    s.d = 3.14;
    s.a[i] = 1073741824;  // 可能越界
    return s.d;
}
```

传入不同的`i`，得到如下结果，`i`大于1时开始写入不属于这个变量的内存，破坏其他变量，得到**无法预测**的结果。

```
fun(0)  ->	3.1400000000
fun(1)  ->	3.1400000000
fun(2)  ->	3.1399998665
fun(3)  ->	2.0000006104
fun(6)  ->	Segmentation fault
fun(8)  ->	3.1400000000
```

有些Unix的系统调用本身就是内存不安全的，比如：
- `gets()`无法确定读取的字符串长度
- `strcpy()` `strcat()`：同样无法确定长度
- `scanf()` `fscanf()` `sscanf()`：当给定`%s`作为读取类型时

**数组越界并不一定每次都会破坏其他数据**，比如有这样的代码读取字符串：

```c
void echo() {
    char buf[4];  // 创建了很小的缓冲区
    gets(buf);
}
```

其对应的汇编代码：

```asm
000000000040069c <echo>:
    sub    $0x18, %rsp      # 在栈上开辟24字节的空间
    
    ... # do something

    add    $0x18, %rsp
    retq 
```

函数**开辟**了24字节的栈帧，但只有低位的四字节*被实际使用*，当数组越界但越界**程度较小**时，数据被写入*未被使用的内存区域*，虽然缓冲区溢出，但未造成其他数据的破坏。但如果输入的字符串长度达到**25**，就开始侵占了原本存放函数返回地址的地方，导致函数**返回地址**改变，函数完成运行后跳转到错误位置，导致程序崩溃。

*如果有这样的一段代码，黑客就能通过注入设计好的字符串，跳转到他们想要的程序位置。*

### 保护内存安全

有多种方式能**保护内存避免攻击**，比如：

- **在代码层面**：
  - 避免使用上述不安全的函数
- **在系统层面**：
  - 在程序开始时，在栈上开辟随机大小的空间，让所有栈帧都后移一个offset，使黑客难以预测位置
  - 将一些内存区域标记为只读
  - 在每个缓冲区前加一个*特殊值*（称为Canary），函数返回时会检测这些特殊值，`GCC`中使用`-fstack-protector` flag开启（现在已经是默认开启了）
